审查基线：`cbb00ec`，v0.3.0。范围覆盖 Go 后端、Vue 页面、配置和追番持久化、磁力匹配、PikPak 下载、MPV 启动、弹幕与远端网页。此次交付为审查报告，没有修改业务代码。

**R01：追番文件缺少完整的读改写事务**

位置：[读取与保存](/home/xjz/WorkPlace/UltimateAnime/app.go:729)、[添加追番](/home/xjz/WorkPlace/UltimateAnime/app.go:532)、[下载完成保存](/home/xjz/WorkPlace/UltimateAnime/app.go:1216)。

添加、取消、标记观看、保存磁力、下载完成均独立读取整个 `followed.json`，再覆盖写回，没有覆盖“读→修改→写”的互斥保护。40 个并发添加的隔离压力测试本次仅保留 2 条记录；这个数字是一次测试结果，不是稳定损失率。真实使用中的桌面/网页同时操作、多个下载完成也会走相同路径。

读取错误直接返回空数组，JSON 解析错误被忽略；隔离测试中损坏的原文件被下一次添加覆盖。写文件采用原地截断，进程退出或写入失败也缺乏恢复保障。`markEpisodeDownloaded` 还忽略保存返回值，可能通知完成但未保存索引。

建议先引入统一的存储层：锁住完整的本地读改写、检查解析错误、同目录临时文件写完后替换、保留备份、向调用方返回持久化失败。耗时网络请求在事务外进行，得到结果后重新读取最新状态合并。任务和多端同步扩展时迁移 SQLite，使用事务与唯一约束。

验收：并发添加、标记、保存磁力、下载完成后所有变更均保留；注入无效 JSON、磁盘写失败和中途退出，原数据可恢复且 UI 明确报错。

**R02：下载缺少幂等性、任务列表和可恢复状态**

位置：[下载入口](/home/xjz/WorkPlace/UltimateAnime/app.go:1076)、[离线轮询](/home/xjz/WorkPlace/UltimateAnime/app.go:969)、[前端临时防重](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Home.vue:460)、[完成事件](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Home.vue:588)。

两次相同 `DownloadEpisode` 都返回 `Started` 并各启动一个任务。前端的 pending 只覆盖准备阶段，收到 Started 后即释放，手动选择候选也没有覆盖下载生命周期的锁。多设备可以重复下载，消耗配额和带宽，并竞争最终路径。

离线准备最多轮询 60 次，未完成即退出，没有持续跟踪机制；云端之后成功也不会自动接续本地下载。下载进度只发桌面事件，当前页面没有对应的进度消费者，网页也没有同类进度广播。错误提示依赖当前正在查看的番剧，换页后很容易错过。

建议建立持久化任务中心：任务 ID、番剧/剧集/资源版本、账号、云端任务 ID、文件 ID、状态、进度、错误、重试次数。对活跃的相同任务返回已有任务。云端仍下载时显示“云端准备中”，超时属于可恢复状态。桌面与网页统一订阅，同时提供状态快照，重连/刷新后补齐。先限制并行任务数，再加暂停、取消和断点续传。

验收：连续点击与两台设备同时提交只生成一个任务；切页、刷新、重连仍可看到进度；离线准备较慢时无需重复消耗配额。

**R03：PikPak 客户端的共享认证状态不支持并发使用**

位置：[请求读取状态](/home/xjz/WorkPlace/UltimateAnime/pkg/pikpak/client.go:63)、[文件列表重置验证码](/home/xjz/WorkPlace/UltimateAnime/pkg/pikpak/client.go:210)、[获取下载地址](/home/xjz/WorkPlace/UltimateAnime/pkg/pikpak/client.go:265)。

同一客户端会被多个下载/列表请求共享，`CaptchaToken` 在请求间读写和清空。并发 `FileList` 的隔离测试已触发 Go data race。验证码还与具体请求 action 相关，单独给某一次赋值加锁不足以保证整个请求使用正确的认证组合。

建议将 action 相关的验证码和请求头作为请求局部数据；共享登录凭据通过不可变快照读取，刷新登录进行串行化或 singleflight。保守修复可先按账号串行化认证 API 阶段，媒体数据传输继续并行。

验收：同账号并发下载、任务轮询、刷新直链和清理查询在 `-race` 下通过，并验证验证码 action 不串用。

**R04：取消追番会清除观看历史和文件关联**

位置：[取消追番](/home/xjz/WorkPlace/UltimateAnime/app.go:706)、[新建条目](/home/xjz/WorkPlace/UltimateAnime/app.go:546)。

`UnfollowLocal` 删除整个条目，观看记录、磁力、下载标记、文件路径一起消失。再次追番会创建空记录，但视频仍留在磁盘。这使“我暂时不追了”变成“应用忘记这部番”，也可能导致重复下载。

建议把“是否追番/收藏状态”“观看历史”“本地媒体索引”分开持久化。取消追番只改变收藏状态；清除历史与删除视频是独立操作。正在下载时取消追番，也不应让下载完成后的文件成为无法检索的孤立文件。

验收：取消后再追，进度和已下载文件仍可识别；取消不删除文件；清除记录有单独入口和明确范围。

**R05：本地删除失败仍丢掉索引，可能显示成功**

位置：[删除逻辑](/home/xjz/WorkPlace/UltimateAnime/app.go:1578)。

`os.Remove` 出错后只写日志，仍无条件删除 `LocalFiles` 和下载标记；如果磁力记录删除成功，整体会返回 Success。文件被占用、权限不足或路径异常时，可能出现“UI 说删除成功，磁盘文件仍占空间”。隔离复现使用无法被 `os.Remove` 删除的非空目录注入错误，确认了此分支行为。

建议区分“文件本就不存在”和真实删除失败；真实失败保留索引并返回明确错误。拆成“删除本地视频”“重选资源”“清除磁力记录”，允许用户选择范围。默认使用回收站可降低误操作成本。

验收：注入删除错误后文件索引仍在；重新删除可恢复；磁力删除成功不能掩盖视频删除失败。

**R06：下载目录设置没有被使用**

位置：[设置字段](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Settings.vue:124)、[实际保存路径](/home/xjz/WorkPlace/UltimateAnime/app.go:1117)。

用户填写 `local_storage.anime_dir`，实际下载始终写到当前工作目录下 `Downloads/<番名>`。这是直接影响磁盘容量和文件查找的功能 bug。

建议以保存的目录为准；相对目录基于稳定的应用数据根目录解析，目录为空时显示实际默认路径。开始任务时检查可写性及剩余空间。番剧目录加入稳定的 subject ID，避免同名或路径字符清洗后发生冲突。改变下载目录应说明只影响新下载，迁移已有文件另行处理。

验收：自定义路径、带空格/中文路径、相对路径、只读路径均有明确一致结果。

**R07：手选候选的宽松策略被直接用于自动下载**

位置：[匹配与排序](/home/xjz/WorkPlace/UltimateAnime/pkg/crawler/client.go:403)、[自动选第一项](/home/xjz/WorkPlace/UltimateAnime/pkg/crawler/client.go:508)。

验收：只有错季候选时自动模式不下载；手选仍可查看并明确知晓冲突；正确季度资源优先。

**R08：长篇动画的集数被硬性限制到 200**

位置：[集数正则与解析](/home/xjz/WorkPlace/UltimateAnime/pkg/crawler/client.go:130)。

`ParseEpisodeNumber` 只接受 1～200，正则也主要限制为 1～3 位数字。第 201、500、1122 集的隔离样例都返回 -1。用户修改搜索关键词仍无法绕过后续的集数过滤。

验收：覆盖 201/500/1122/12.5/S02E01/合集/1080P/年份，精确检验预期结果。

**R09：旧详情响应会覆盖新选中的番剧**

位置：[Home 详情加载](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Home.vue:311)、[Discovery 详情加载](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Discovery.vue:296)。

**R10：我的追番中的文件丢失恢复不完整**

位置：[Home 本地播放](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Home.vue:402)、[Discovery 的恢复分支](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Discovery.vue:421)。

**R12：更新提醒把“今天会播”当成“已经更新”**

位置：[更新判断](/home/xjz/WorkPlace/UltimateAnime/frontend/src/utils/updateReminders.js:24)、[打开详情清除提醒](/home/xjz/WorkPlace/UltimateAnime/frontend/src/views/Home.vue:311)。

验收：播出前后、延期、跨时区、同日多集、打开详情但未观看均有清楚一致的状态。

**R13：单一颜色无法表达剧集多维状态**

**R14：配置生效、保存与首次加载需要统一约定**

验收：模拟弹幕服务一直慢响应，视频仍及时完成并可播放；弹幕失败只影响弹幕入口。

**与主流视频网站相比，应该补上的使用逻辑**

以下参考公开产品页面和官方帮助，具体方案是针对本项目的设计建议。

| 参考产品 | 已核实的做法 | 本项目可采用的方式 |
|---|---|---|
| Netflix | 继续观看列表支持移除；下一集自动播放有独立开关 | 首页给“继续第 N 集”入口，用户可以移出该区域；连播可关闭，并提供取消机会。[继续观看](https://help.netflix.com/en/node/115312)、[自动下一集](https://help.netflix.com/en/node/121518) |
| YouTube | 缩略图进度条展示上次看到的位置，重新播放通常续接 | 番剧卡片展示“第 4 集 · 12:36”，主按钮从该位置继续。[播放进度条](https://support.google.com/youtube/answer/7174115?hl=en-GB) |
| Crunchyroll | 可通过可见菜单标记单集、整季、整部为已看 | 用“⋯”菜单承载标记已看、标记前 N 集、重看和下载操作；鼠标快捷键作为补充。[官方操作说明](https://help.crunchyroll.com/hc/en-us/articles/31320247305748-How-do-I-mark-episodes-seasons-and-shows-as-watched) |
| Bilibili 番剧区 | 分开提供连载、完结、最近更新、新番时间表、番剧索引 | “发现”同时提供时间表、最近更新、全年/历季索引和搜索，兼顾追新与补番。[番剧区](https://www.bilibili.com/anime/) |
| Bangumi | 章节进度、每日放送、分类/标签、作品资料关系清楚 | 将个人进度与播出信息分开，并让作品详情成为统一入口。[官方首页](https://bangumi.tv/) |

**建议的主要用户路径**

用户打开应用后，首先应该能回答：“接着看什么”“我的番更新了吗”“下载好了吗”。首页推荐排列为继续观看、已更新未看、今日放送、我的片库。每张卡片展示观看位置、待看数量和资源可用性，添加日期降为次要信息。

详情页主按钮随状态变化：有观看位置时“继续第 4 集 12:36”；未开始时“播放第 1 集”；本地没有文件时提供“在线播放”和“下载到本机”这两个明确选择；正在准备时显示任务状态；资源暂缺时提供重新搜索或订阅。用户不应从鼠标左键隐含的规则猜测接下来是播放还是下载。

当前 `PlayMagnet` 虽然在后端实现，但两个主要页面仅导入，没有实际调用；默认路径仍是完整下载之后再本地播放。可以先给桌面端补齐可见的在线播放入口，同时把受账号绑定的播放会话、直链刷新和下载任务分开设计。远端网页当前定位为家中电脑的管理面板，这是现有能力边界；手机直接观看应作为独立扩展，并明确“在此设备播放”和“在家中电脑播放”。

当前没有前端番剧搜索入口；`SearchBangumi` 在后端存在。只有当季日历会使补旧番、寻找 OVA/剧场版困难，也使已离开日历的收藏难以从现有入口取消。建议提供统一搜索、按季度/年份/状态筛选、从我的片库管理收藏，以及独立详情路由。

README 描述的 Bangumi 在看同步、看过/抛弃管理，在当前主要前端页面没有接通。应先校正文档能力说明，再实现显式同步：展示账号、上次同步时间、待同步变更与冲突处理。本地观看记录和远端收藏状态都应有独立的真实来源。

**观看进度应成为一等数据**

当前应用只保存已看集数，启动 MPV 后没有读取播放位置、结束原因或实际观看完成情况。用户自己的 MPV 配置可能实现播放器内部续播，但应用本身仍不知道看到哪里，因此无法可靠提供继续观看、自动标记和下一集。

建议通过本地 MPV IPC 订阅播放属性和结束事件，保存 episode ID、媒体版本、位置、时长、最近观看时间、完成状态。定时及暂停/退出时保存，避免每帧落盘；自动已看规则结合观看比例和正常结束，支持手动覆盖。单纯启动播放器或拖到末尾不应直接推断完整看过。MPV 官方支持 JSON IPC 和读取 `time-pos`，亦有 `--save-position-on-quit` 可作为短期播放器层续播措施。[MPV 官方手册](https://mpv.io/manual/stable/#json-ipc)

**拆开状态，避免用一个颜色或一个列表承担所有含义**

| 维度 | 建议状态 | 不应产生的联动 |
|---|---|---|
| 收藏 | 想看、在看、看过、搁置、弃番、未收藏 | 取消收藏不删除观看历史或媒体 |
| 播出 | 未播、播出中、完结、延期、未知 | 电视已播不代表资源已上架 |
| 资源 | 未检索、可用、待核对、暂无资源 | 找到磁力不代表云端下载成功 |
| 下载 | 排队、云端准备、本地传输、完成、失败、取消 | 下载完成不等于看过 |
| 观看 | 未开始、部分观看、看完、重看 | 打开详情不算观看 |
| 通知 | 未读、已读、已忽略 | 清除提醒不清除待看集数 |

各状态建议绑定稳定的 subject ID / episode ID。当前大量操作以浮点 `sort` 作为主键，后续加入 SP、OVA、绝对集数和重制版时应保留 sort 为显示/匹配信息，正式条目以稳定 ID 标识；未收录的占位剧集建立独立临时 ID，并设计元数据补齐后的合并规则。

**可以较快改善的交互细节**

- 剧集与卡片使用真正的 button/link，支持 Tab、Enter、Space；详情和磁力弹窗补齐 Esc、焦点约束、关闭后焦点恢复和背景滚动锁定。当前详情不是路由，手机返回键无法自然关闭详情，建议接入路由历史。
- 将“右键标记、中键删除”改为可见的“⋯”菜单，同时保留熟练用户快捷操作。确认删除时允许选择视频、磁力、历史的范围。
- 成功提示使用非阻塞 toast，任务失败进入通知/任务中心并提供重试。需要作出决定时才使用确认对话框，减少连续 alert 打断。
- 首次启动显示简短配置向导：检查 MPV、选择下载目录、测试网络与账号。账号密码改为逐账号配置，避免用户必须给所有账号设同一个密码。
- “隐藏完结”明确为隐藏播出完结作品；更实用的默认过滤是“隐藏我已看完”，让完结但没补完的番继续出现。
- 资源候选解析出字幕语言、字幕组、分辨率、编码、内嵌/外挂、大小；记住用户在同一作品上的选择，保留更换版本入口。包含多个视频的资源必须按集匹配或弹出文件选择，当前只选目录内最大视频不适合作为通用规则。
- 日志保留为诊断入口；增加级别筛选、搜索、复制和暂停自动滚动。当前用户向上查看仍会被新日志滚到底部，“清空”也只清当前页面，换页后旧历史会回来。
- 首页加载失败显示错误与重试，不能继续呈现“你还没有追番”的空状态；图片加载失败给统一占位图。

网页播放需要按容器、编码、字幕格式判断直接播放或转码，不能假设把下载地址交给浏览器就能覆盖现有 MPV 的格式能力。OP/ED 跳过应按作品/版本记录并允许手动纠正，不宜统一跳固定 90 秒。推荐系统可先用用户收藏、标签、评分和可解释的规则，等观看数据稳定后再考虑复杂模型。

**代码组织与回归保障**

优先拆出存储层、下载任务服务、播放器会话服务、资源匹配策略；将 Home/Discovery 共享的详情、选集、磁力候选、错误恢复合并。后端逐步改用结构化错误码与状态对象，避免前端解析 `Error: FileMissing`、Success、Started 等字符串来决定行为。

值得新增的回归场景：两端同时改同一部番、下载完成与取消追番同时发生、重复点击、文件删除/写入失败、旧响应晚到、云端任务超时后完成、SSE 断线恢复、账号切换时另一个任务还在下载、长篇与特别篇匹配、Windows 带空格路径。端到端流程至少覆盖首次配置→追番→选资源→下载→播放→退出续播，以及仅用键盘/手机完成主要操作。

本轮优先建议是：先保障已有数据和下载正确性，再完成继续观看与任务中心，随后增加搜索、同步和自动订阅。这样后续功能建立在可恢复、可解释的状态之上。
